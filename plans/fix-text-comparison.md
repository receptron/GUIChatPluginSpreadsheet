# fix: 比較を Excel の比べ方で計算する（文字・真偽値・& を含む比較）(#81)

## 何が起きていたか

評価器の比較の道は、数だけを受け付けていた（`isSafeComparison` を通った式を JS に渡す）。

- `=A1&B1="12"` や `=C1="x"` は計算されず、式の文字がそのまま返った
- 式全体が `"` で始まり `"` で終わり、`&` を含まなければ「文字一つ」として扱う近道があり、`="a"="b"` はそこで文字として返った
- 数どうしでも、`<>` は JS に訳されず `#ERROR!`、連なった比較は JS の読み方（`1<2<3` が TRUE）、0 で割ると `Infinity` のまま比べていた

## 直し方

- `src/engine/textComparison.ts`（純粋な関数）：一番外側の比べる記号で式を分ける（`splitTopLevelComparisons`）、Excel の並べ方で比べる（`compareCellValues`）、左から順にたたむ（`foldComparisons`）
  - 数 < 文字 < 真偽値。文字どうしは大文字小文字を区別しない。数と文字は等しくならない
  - Excel に無い記号（`==` `!=`）や、片側が空のときは null を返し、今までの道に任せる
- 評価器：一番外側に比べる記号があれば、各側を今の道（`&` のつなぎ、計算、文字一つ、`TRUE`/`FALSE`）で計算して比べる。どれか一つの側でも計算できなければ、今までどおり式の文字を返す
- `&` の処理を `evaluateConcat` に切り出し、式全体と比較の各側の両方で使う
- 文字一つの近道は、本当に文字一つだけの式（`isLoneLiteral`）に限る
- `IF` の条件も評価器を通るので、同じ比べ方になる（`=IF(1="1",…)` は Excel と同じく偽）

## 範囲外（前からの不具合）

- 大文字の `TRUE` / `FALSE` を `&` や計算の中に書くと計算されない（`=FALSE&2`、`=TRUE+1`）
- 文字を計算に入れると `#VALUE!` にならない（`=0*("a"&1)` が `#DIV/0!`、`=("a"&1)+1` が `a11`）
- 括弧の中の比較（`=("a"="b")&"x"`）は、今までどおり計算されない
- `IFS` の条件は `condition.ts` が別に比べる（文字の `=` が大文字小文字を区別する）。今回は触らない

## 確かめたこと

- `textComparison.ts` の例と、並べ方の性質（逆にすると符号が逆になる、並べ替えた結果が参照用の並べ方と一致する）を作った値で確かめるテスト
- エンジンを通して、作った比較の式を、テストに書いた参照用の比べ方と照らし合わせる（種を表示する。`COMPARISON_SEED` で再現できる）
- 古い実装と並べてエンジンの結果を比べた
  - 比べる記号を含まない式：値が変わったのは `="1/2/2020"/"1/2/2020"` が 1 になる場合だけ（Excel も 1）。ほかの差は、計算できない式で返る文字が変わっただけ
  - 文字や `&` を含む比較：古い実装が値を返していた式で、答えが変わったものは無い
  - 数だけの比較：差は「0 で割ると #DIV/0!」「連なりを左から Excel の比べ方で読む」「`<>` を計算する」の 3 種類だけ
- 実装をわざと壊すと（大文字小文字を区別する、型の順を入れ替える、括弧や文字の中の記号を数える、連なりの最初だけ比べる、など）、記号の並び順を変える一つ（動きが変わらない）を除き、どれもテストが落ちる
